# M7 — Multi-Tool Workflows

## Feature I picked
- Note search: free-text filter against title and body from the notes list view.

## Plan from chat
Data model: No changes to the note dict shape needed — search filters the existing in-memory list at render time rather than storing anything new.

Routes: Add an optional query parameter q to the existing home route (/). If q is present, filter pp.notes to only notes where q appears in the title or body (case-insensitive). Pass q back to the template so the search box stays populated.

UI: Add a search form at the top of the notes list (index.html) with a single text input and a submit button. The form uses GET so the query appears in the URL and is bookmarkable.

Edge cases: empty query should return all notes; whitespace-only query should be treated as empty; search should be case-insensitive; notes with no match should produce an empty list with a friendly message.

## Workflow retro
For this feature I used all four lanes of the conductor model. Chat handled the planning phase — I described note search and asked for a one-page design covering data model, routes, UI, and edge cases. This was the right call because it produced a clear written plan I could paste directly into Claude Code without back-and-forth about scope.

Claude Code handled execution. The handoff worked well: the chat plan gave Claude Code enough structure that it proposed a correct implementation on the first try. The one thing Claude Code caught that chat missed was the specific implementation detail of stripping and lowercasing the query before comparison — chat described the edge case but left the how unspecified.

Copilot handled polish. Renaming a variable and adding a docstring took about ten seconds each using Tab completions. This would have been wasteful to brief an agent for — Copilot's fluency advantage is real for changes smaller than a sentence.

Chat handled review. Pasting the diff into a fresh chat session with no investment in the code found the missing empty-results message immediately. This is the highest-leverage use of chat in the loop and something I would do on every real PR.

The parallel sessions experiment was honest: I did not actually parallelize effectively. Switching between two terminals while both agents were active was harder to track than expected. The right use of parallelism is probably starting a second task while the first agent is running a long test suite — not while it is actively planning and needs review.

If I re-did this feature I would write the empty-results UI into the chat plan upfront so Claude Code included it in the first pass rather than needing a review-cycle fix.
